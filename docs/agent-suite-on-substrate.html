How an Agent Suite can run on Substrate

Kaimahi defines, publishes, inspects, and lifts the immutable suite. AgentSessions provides durable member sessions and observable hand-offs. Substrate supplies one independently suspendable Actor for each active agent.

Branch poc/agentsuite

The issue #273 experiment now has an executable release and aggregation path

The sample suite contains one coordinator and two specialists. Kaimahi strictly resolves their exact portable documents, computes immutable member and suite identities, exports a standards-shaped OCI Image Layout, and can execute three durable AgentSessions turns: purchasing, receiving, then coordinator aggregation.

Resolve

Strict suite graph

The entry point, member roles, local source paths, declared allowedAgents, and aggregation inputs must agree. Unknown YAML fields, duplicate members, path escapes, and unsupported runtime behavior fail closed.

Package

OCI Image Layout

The layout contains a resolved JSON config, exact suite.yaml, exact member agent.yaml layers, an OCI artifact manifest, and index.json. Credentials and session state are excluded.

Run

Explicit aggregation

Each specialist gets an independent durable session and Substrate Actor, then is suspended after its output commits. Their recorded outputs become labeled inputs to the coordinator's third session, which produces the only stdout answer.

kmx suite inspect /tmp/invoice-review-oci

kmx suite run ./examples/agent-suite/invoice-review \
  --server 127.0.0.1:18080 \
  --project agentsuite-poc \

Declared side

The Agent Suite is the immutable release boundary

The authored suite can use local agent paths. Before publication, Kaimahi resolves every member to an immutable revision and produces a suite digest over the resolved graph.

What the OCI Image Layout contains

The POC writes a standard OCI Image Layout directory. Files are addressed by their content digest; the small JSON descriptors connect the root index to one Agent Suite artifact manifest, then to the resolved suite config and exact authored YAML layers.

One exact suite.yaml layer and one exact agent.yaml layer per member make inspection and provenance possible without rebuilding from mutable paths.

How the layout is used

  1. Package locally — implemented. kmx suite package resolves and validates the graph, writes content-addressed blobs, then writes the manifest and root index.
  2. Inspect and verify — implemented. kmx suite inspect /path/to/layout rejects unknown JSON fields, wrong media or artifact types, missing blobs, size mismatches, digest mismatches, incomplete config, or a suite annotation that does not match the config digest.
  3. Push and resolve through a registry — next. Standard OCI tooling can transport the same descriptors and blobs. A mutable tag is only a lookup convenience; lift must pin the returned manifest digest.
  4. Lift the pinned release — proposed. Kaimahi reads the resolved config, admits each exact member, installs or reuses the matching ActorTemplate, and records a deployment receipt binding suite digest to target resources.
Identity rule: the suite digest is the sha256 digest of the canonical resolved config. The manifest has its own digest because it also covers the source-layer descriptors and annotations. Both are useful: one identifies suite semantics; the other identifies the complete transport artifact.

Current POC includes

The exact suite and agent source bytes, member names and roles, portable digests, model names, entry point, aggregation graph, runtime name, and required capabilities.

Deliberately excluded

Credentials, cluster-specific secrets, live session UIDs, Actor addresses, mutable runtime history, and model conversations.

Not yet in the artifact: registry signatures, provenance attestations, semantic version policy, evaluation bundles, harness-image descriptors, ActorTemplate bindings, and deployment receipts. Those are future release and lift contracts, not hidden POC behavior.

Deployment side

Lift resolves the suite once, then prepares every member

Kaimahi should bind deployment to the suite digest, not continue following a mutable tag. Each member becomes a registry entry that maps an AgentSessions harness ID to a Substrate ActorTemplate and its required capabilities.

  1. Resolve the OCI tag to one suite digest. Fail or require renewed consent if a previously reviewed tag moved.
  2. Validate every member. Confirm member digests, coordination references, harness descriptors, model/tool bindings, and target capabilities.
  3. Install or verify ActorTemplates. Pin each harness image by digest; never lift a moving image tag as the reviewed revision.
  4. Configure the AgentSessions host registry. Register one Placer per suite member, each backed by the corresponding Substrate Runtime backend.
  5. Record a suite deployment receipt. Bind the suite digest to target identity, member digests, ActorTemplate identities, and AgentSessions endpoint.
  6. Report partial outcomes honestly. A suite is not Ready when one required member failed admission or registration.
Requested:   ghcr.io/acme/invoice-review:v1
Resolved:    ghcr.io/acme/invoice-review@sha256:aaaa...
Target:      production/agents
Runtime:     agentsessions-substrate

Plan:

  reuse   receiving-agent     @ sha256:3333...

No session is created during lift.
Actors are created lazily when a member first executes.
Why lazy Actors? The Suite is a release and deployment unit, not a request to keep every agent running. AgentSessions can create the entry-point Actor on the first turn and create helper Actors only when delegation actually happens.

Execution side

One suite run, multiple durable sessions

The coordinator and each helper should have a separate AgentSessions session. This gives every member its own event log, fence, compute lifecycle, replay boundary, and Substrate Actor.

Control and model-effect flow Durable evidence and final output Session-to-Actor lifecycle Actor/provider trust boundary
The important interaction is session-to-Actor, not Actor-to-Actor. The purchasing, receiving, and coordinator Actors never call each other directly. Kaimahi drives the current POC sequence through AgentSessions; committed specialist outputs cross the boundary as typed, labeled inputs to the coordinator's durable session.

How delegation should work
  1. The coordinator calls a controller-mediated agentsessions.delegate tool with target member, input, and idempotency key.
  2. The host verifies the target is allowed by the deployed suite digest—not merely by a caller-supplied name.
  3. The host creates a distinct helper session using that member's harness and immutable agent digest.
  4. The parent journal records the hand-off intent before the child executes; the child stores the same hand-off ID and parent session identity.
  5. The helper's first Exec lazily creates or resumes its own Substrate Actor.
  6. The helper result is recorded, linked back to the hand-off, and returned to the coordinator.
  7. Crash recovery uses the idempotency key and durable hand-off state so the helper is not created or executed twice.
Do not use AgentSessions Fork for cross-agent delegation. Fork deliberately inherits the parent's harness and model because it branches the same workload. It is ideal for parallel hypotheses or cloned state of one agent, but it cannot select a different suite member.

Authoring and projection sides

Canvas can edit the physical Agent Suite and observe its runs

An Agent Suite is the complete physical, on-disk representation of the system: its suite.yaml, member directories, and exact agent.yaml documents. Canvas can be the full editing experience over that representation, while the same product surface can project durable runtime evidence without inventing a second source of truth.

Build Canvas

Write-through suite editing

Open a suite directory as a graph, mutate members and relationships through UI gestures or automation, then write the change back to the physical files. Source control, strict parsing, and the resulting digest remain authoritative.

Run Canvas

Read-only evidence projection

Bind the immutable suite and member revisions to AgentSessions records, then render sessions, hand-offs, lifecycle state, outputs, and missing evidence without changing the released source.

One Canvas, two authority models: authoring gestures are commands that mutate the on-disk Agent Suite; runtime views are projections that read durable AgentSessions evidence. Canvas should never become a shadow task or suite database that can drift from either source.

Editing round trip

  1. Open the physical suite. Read suite.yaml and every referenced portable agent document into one editable graph.
  2. Apply a typed mutation. A UI action, CLI command, or other tool adds, removes, renames, reconnects, or configures an agent through the same mutation contract.
  3. Write the affected files. Update the suite graph and member documents together so relationships such as entry point, roles, allowedAgents, and aggregation inputs cannot drift.
  4. Reparse and validate from disk. The strict Suite reader is the acceptance boundary; unknown fields, broken references, duplicate members, unsafe paths, and incompatible portable behavior still fail closed.
  5. Show the semantic diff and new identity. Canvas presents the changed files, graph-level meaning, validation result, member digests, and recomputed suite digest before package or commit.

Mutation boundary: Canvas should not directly patch arbitrary YAML fragments. It should issue typed suite operations, write complete affected documents, and accept the edit only after reopening the files through the same strict resolver used by kmx suite inspect.

Recommended implementation order

Prove identity and safe mutation before building the full Suite Canvas

Phase 1

One suite, fixed target

POC implemented: coordinator plus two specialists, suite/member digest annotations, durable member sessions, and explicit final aggregation. Per-member ActorTemplates remain a lift concern.

Phase 2

Durable delegation

Add the mediated delegate operation, child session creation, hand-off identity, at-most-once recovery, and parallel helper execution.

Phase 3

Build + Run Canvas

Add typed, write-through editing of the physical suite with strict round-trip validation; project one real run into runview and label missing, unreadable, or mismatched evidence.

Phase 4

OCI release and lift

Local OCI Image Layout export is implemented. Registry push/pull, tag resolution, semantic diff, deployment receipts, partial outcomes, status, and evaluation remain.

First end-to-end acceptance test

  1. Publish a suite with coordinator, purchasing, and receiving member digests.
  2. Lift it to one AgentSessions host backed by Substrate.
  3. Start one coordinator session annotated with the exact suite digest.
  4. Delegate two checks in parallel, creating two helper sessions and two Actors.
  5. Suspend the idle purchasing Actor while receiving waits for input.
  6. Reconnect the Canvas and resume from durable cursors without duplicated events.
  7. Show declared relationships separately from the two observed hand-offs.
  8. Bind every participant to its immutable member digest; deliberately remove one binding and show missing, not failed.
  9. Replay one stateless helper and prove no model or tool effect is repeated.
  10. Move the suite tag and confirm the historical run still displays the deployed digest.
